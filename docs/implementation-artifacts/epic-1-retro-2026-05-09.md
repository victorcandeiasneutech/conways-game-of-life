## 🔍 Challenges and Learnings

Bob (Scrum Master): "Now the harder part. Where did we struggle?"

### 1 — Architecture deviations required mid-story correction

Charlie (Senior Dev): "Story 1.2 had four architecture deviations that needed fixing after initial implementation: tags in `package.json` (should be `project.json`), missing tsconfig path aliases, wrong ESLint `allow` value, and missing `project.json` files for apps. None of these were caught pre-implementation."

Alice (Product Owner): "The root cause is that Nx 22.7.1 generators don't emit `project.json` automatically — the architecture assumed they would. That's a gap between the architecture spec and the actual generator behaviour."

**Lesson learned:** When generator output diverges from architecture expectations, document the divergence explicitly in the story's Dev Notes *before* implementation. Don't assume generator defaults match the spec.

---

### 2 — TypeScript 5.9 `baseUrl` requirement was a surprise

Charlie (Senior Dev): "When story 1.6 made `libs/ui` affected for the first time, we hit `TS5090: Non-relative paths are not allowed when 'baseUrl' is not set`. This is a TypeScript 5.9 requirement — `paths` values without leading `./` need `baseUrl` when `moduleResolution: bundler` is in use."

Dana (QA Engineer): "It had been there from story 1.2 but never triggered because `libs/ui` was never in the affected set before. The fix (`baseUrl: "."` in `tsconfig.base.json`) is small, but the surprise cost us a CI iteration."

**Lesson learned:** When introducing a new project to the affected set for the first time, explicitly verify its typecheck passes locally before opening the PR. Don't assume it was always fine just because CI never ran it.

---

### 3 — Scaffold noise in `libs/ui` (CSS module import)

Charlie (Senior Dev): "The generated `ui.tsx` imported `./ui.module.css` with no type declaration. The `@nx/react/typings/cssmodule.d.ts` reference in `tsconfig.lib.json` was the bridge, but it required `baseUrl` to resolve — a circular dependency with problem #2 above."

Bob (Scrum Master): "The fix was to delete the scaffold component entirely. It was going to be replaced in story 3.1 anyway."

**Lesson learned:** For generated libs with no real content yet, delete scaffold placeholder components (`ui.tsx`, `ui.module.css`) immediately after generation rather than leaving them to cause confusion later. An empty `export {};` is cleaner than broken scaffold code.

---

### 4 — GitHub Actions self-approval requires an explicit repo setting

Dana (QA Engineer): "Story 1.6 got blocked because `github-actions[bot]` couldn't post approvals that count toward required reviews. The fix — Settings → Actions → General → 'Allow GitHub Actions to create and approve pull requests' — isn't obvious."

Alice (Product Owner): "This should have been in the story's Dev Notes from the start. It's a one-time repo configuration that isn't documented in the `hmarr/auto-approve-action` README prominently."

**Lesson learned:** When a workflow depends on a non-default GitHub repository setting, document that setting explicitly in the story's Dev Notes as a prerequisite step.

---

### 5 — Direct push attempts against branch protection

Bob (Scrum Master): "Early in story 1.6 development, there were attempts to commit sprint-status updates directly to `main`. Branch protection blocked them, which is the correct behaviour — but the workflow around 'where does the sprint-status update live' needed clarification."

**Lesson learned:** Sprint-status updates (marking a story done) belong in the same PR that implements the story, not as a follow-on direct push. The correct workflow is: implement on feature branch → update sprint-status → PR → merge.
