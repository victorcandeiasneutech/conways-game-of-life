## 🎉 What Went Well

### 1 — Architectural payoff from story 2.1

The `Uint8Array`/`ArrayBuffer` flat grid design — chosen in story 2.1 for cache-friendliness — enabled zero-copy transferables in story 6.1 with zero changes to `libs/sim`. The architecture doc had called this out explicitly as the upgrade path. The implementation confirmed it: no refactoring, just wiring.

**Pattern:** Boring, correct data structures compound. The `boolean[][]` alternative would have required a full rewrite of the grid representation before the worker could be introduced.

### 2 — Clean three-message worker protocol

The `init` / `tick` / `render` protocol that emerged in story 6.2 is legible, minimal, and handles the three distinct cases cleanly: one-time setup, hot simulation loop, and paused-state redraw. The intent of every branch in `onmessage` is immediately readable without tracing message shapes.

### 3 — Type-driven refactor surfaced a real latent bug

Adding `WorkerResponse` to type the outbound `postMessage` (caught in code review) immediately revealed that `next.cells.buffer` is typed as `ArrayBufferLike`, not `ArrayBuffer` — a mismatch with the `WorkerResponse.buffer: ArrayBuffer` field. The cast (`as ArrayBuffer`) is correct and safe, but the type system caught an inconsistency that had been silently passing. This is the best kind of quality improvement.

### 4 — Zero technical debt, zero incidents

Both stories shipped cleanly. No shortcuts taken on the worker protocol, no deferred cleanup, no unresolved edge cases in the OffscreenCanvas sizing logic.

## 🔍 Challenges and Learnings

### 1 — Feature branch created after code, not before (2 / 2 stories)

Both stories had all implementation work sitting unstaged on `main` at code review time — no branch, no commit. The code review was the catch mechanism both times, which is acceptable, but the slip was consistent.

**Root cause:** Execution habit, not a missing process. The pattern (feature branch → implement → PR) is correct and established.

**Fix:** Branch first, code second. No process change required — awareness carry-forward only.

### 2 — Custom Nx `nx:run-commands` typecheck target requires explicit `dependsOn`

When the inferred Nx typecheck target was replaced with a custom `nx:run-commands` target in story 6.1 (to run both `tsconfig.json` and `tsconfig.worker.json`), the implicit `dependsOn: ["^typecheck"]` was lost. This caused a CI failure: `TS6305 — output file .d.ts cannot be found` because `libs/sim` and `libs/types` hadn't built their declaration files before `web` typechecked against them.

**Fix applied:** `"dependsOn": ["^typecheck"]` added to `apps/web/project.json` custom target.

**Carry-forward:** Any new app with a custom typecheck target (e.g., `apps/api` in Epic 7) must include `dependsOn` explicitly.

### 3 — TypeScript `webworker`/`dom` lib isolation was multi-step

Isolating the worker from the main tsconfig required three coordinated changes: a separate `tsconfig.worker.json` (lib: webworker), excluding worker files from `apps/web/tsconfig.json`, and a custom Nx target running both tsconfigs sequentially. The complexity was higher than the story estimate suggested but was self-contained to Epic 6 infrastructure.
