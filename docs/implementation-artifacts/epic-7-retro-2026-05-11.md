## 🎉 What Went Well

### 1 — Architecture §5.4 matched implementation exactly

The `PatternRepository` interface, `SavedPattern` type, and SQLite schema were all defined in architecture §5.4 before a single line of code was written. In story 7-1, the types were copied from the architecture doc verbatim. In story 7-4, the Prisma schema matched the documented column set without negotiation.

**Pattern:** Upfront type design eliminates rework. The fact that swapping `InMemoryPatternRepository` for `SqlitePatternRepository` required zero changes to `PatternsService` or `PatternsController` is proof.

### 2 — `PATTERN_REPOSITORY` injection token — clean DI seam

The string-token + `useExisting` alias pattern (`{ provide: PATTERN_REPOSITORY, useExisting: SqlitePatternRepository }`) gave us a proper interface boundary inside NestJS. `PatternsService` depends on `PatternRepository` (a types lib interface), not on any concrete class. The module wires the implementation. This is the correct structure for a repository pattern in NestJS.

**Pattern:** Injection tokens decouple the service from the implementation at the framework level, not just at the TypeScript type level. The `InMemoryPatternRepository` remains a valid, tested implementation that can be re-wired for testing without mocking.

### 3 — In-memory SQLite contract tests — no filesystem side effects

The `prisma.repository.spec.ts` suite uses `file::memory:?cache=shared`, sets `process.env['DATABASE_URL']` at module scope before `new PrismaService()` is called, creates the schema with a single `$executeRawUnsafe` call, and resets state with `prisma.pattern.deleteMany()` in `beforeEach`. The five contract tests cover the full `PatternRepository` interface surface.

**Pattern:** In-memory SQLite for Prisma tests is fast, self-contained, and filesystem-clean. The `$executeRawUnsafe` DDL approach avoids running the migration runner inside Jest — simpler and more predictable.

### 4 — Component and helper extraction discipline in 7-3

Story 7-3 extracted `SavePatternPanel` as a fully controlled component (no internal fetch calls) and `extractLiveCells` / `gridFromSavedPattern` as pure, framework-free helpers. This yielded 7 unit tests on pure functions before any UI render test touched the component.

**Pattern:** When adding UI features, push logic into pure helpers first. The controlled component pattern keeps state in `page.tsx` where it belongs; the helpers are independently testable and reusable.

### 5 — Zod validation at the api-client boundary

`libs/api-client` validates every API response with zod schemas. If the NestJS API changes its shape, the client fails loudly at the parse step — not silently downstream as a runtime type error. The `as unknown as SavedPattern` cast bridges the zod output type to the readonly tuple type safely.

**Pattern:** Parse at the boundary, trust inside. The web app never receives an unvalidated API response.

## 🔍 Challenges and Learnings

### 1 — Prisma 7 breaking change hit on install

The first `pnpm add @prisma/client prisma` pulled Prisma 7 (latest). Prisma 7 removed the `url` field from `datasource` in `schema.prisma`, replacing it with a driver adapter model. This was a breaking change not flagged in any story dev notes.

**Error encountered:** `The datasource property 'url' is no longer supported.`

**Fix:** Pinned to `prisma@^5.22.0` and `@prisma/client@^5.22.0` — the version the architecture was written against.

**Carry-forward:** When installing any major-version dependency, check the changelog for breaking changes before writing implementation code. For Prisma specifically, the architecture doc version should be pinned in the story dev notes.

### 2 — pnpm v10 `onlyBuiltDependencies` blocked prisma generate in CI

pnpm v10 introduced a security gate: postinstall scripts are blocked by default unless the package is listed in `onlyBuiltDependencies`. `@prisma/client`'s postinstall runs `prisma generate` — which produces the typed client. In CI with `pnpm install --frozen-lockfile`, the client was never generated, so tests failed with import errors at runtime.

Bob (Scrum Master): "Two CI failures on the 7-4 branch — first typecheck (stale cache, no code change needed), then test (prisma generate missing in CI). The second required real diagnosis."

**Fix:** Added `"pnpm": { "onlyBuiltDependencies": ["@prisma/client", "prisma"] }` to root `package.json`, AND added an explicit `pnpm prisma generate --schema apps/api/prisma/schema.prisma` step to the CI test job. The explicit step is the reliable fix in a monorepo where postinstall may not find the schema.

**Carry-forward:** Any story adding a dependency with a postinstall script in a pnpm v10 workspace must add it to `onlyBuiltDependencies`. For Prisma specifically, the explicit generate step in CI is mandatory.

### 3 — Feature branch discipline slipped again on 7-4

Epic 6 action item #1 was "create feature branch before writing any code." In story 7-4, implementation began before the branch was created — the user had to intervene to get the branch set up. This is the second epic in a row where this pattern repeated.

Bob (Scrum Master): "That's a straight-up miss on our most-repeated action item. Second epic in a row."

Amelia (Developer): "The branch-first habit just isn't wired in yet. The work feels urgent and you start typing."

**Root cause:** Execution habit. The correct pattern is known; the automation to enforce it isn't there.

**Carry-forward:** SM must make "create branch" the first explicit task in every story dev notes, not just a facilitation note.

### 4 — DATABASE_URL path resolution confusing under Prisma

Prisma resolves `file:` relative paths in `DATABASE_URL` relative to the **schema directory** (`apps/api/prisma/`), not the process CWD. This caused the initial migration to create `patterns.db` at the wrong location.

**Fix:** Use `file:../data/patterns.db` (up one level from `apps/api/prisma/` → `apps/api/data/`). For the NestJS runtime from `apps/api/`, the `.env` uses `file:../prisma/../data/patterns.db`... wait, actually the runtime CWD is `apps/api/` and the env var is read by NestJS, not Prisma schema — `file:./data/patterns.db` resolves correctly from `apps/api/`.

**Carry-forward:** Document Prisma's schema-relative path resolution in any story that configures `DATABASE_URL`. It trips up everyone the first time.

### 5 — `apps/web/tsconfig.json` path alias not auto-added by Nx sync

When `libs/api-client` was added as a dependency of `apps/web` in story 7-3, Nx sync added the project reference to `tsconfig.json` but did NOT add the `paths` entry for `@conways-game-of-life/api-client`. The Next.js webpack resolver requires the path alias for module resolution.

**Fix:** Manually added `"@conways-game-of-life/api-client": ["libs/api-client/src/index.ts"]` to `apps/web/tsconfig.json`.

**Carry-forward:** When wiring a new lib into `apps/web`, always check that `tsconfig.json` `paths` has the alias entry — Nx sync does not handle this automatically.
