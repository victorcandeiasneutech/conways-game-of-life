## 🎉 What Went Well

### 1 — Existing architecture absorbed the new feature with zero disruption

Bob (Scrum Master): "Epic 8 is the proof-of-concept for every architectural decision made since Epic 2."

Winston (Architect): "Story 8-1 was purely additive. `RuleSet` interface — already in `libs/types`. `conwayRules` — already exported. The only change to existing files was adding one export line to `libs/sim/src/index.ts`. The architecture was genuinely open for extension."

Amelia (Developer): "And module boundaries held. `libs/sim` imports only from `libs/types`. No new violations. The boundary lint would have failed CI if we'd tried to reach across it."

**Pattern:** When the type boundary and interface design are done upfront, adding a second implementation of anything — a rule set, a repository, a renderer — is a one-file-plus-export job. Epic 8 confirmed what Epic 7 demonstrated: the abstraction earns its keep at story 2, not story 1.

### 2 — Worker message protocol extended cleanly with the serializable-ID pattern

Amelia (Developer): "The key insight was: postMessage transfers data, not behavior. You can't send `highLifeRules.step` through a message — you send `'highlife'` and let the worker do the lookup. That constraint leads to a cleaner boundary anyway."

Winston (Architect): "The `activeStep` variable inside the worker is exactly right. The worker owns its execution state. The main thread owns the selector state. The message is the interface."

Victor (Project Lead): "And because we defaulted `activeStep` to `conwayRules.step` inside the worker, a freshly-initialized worker is always consistent with the UI's default without needing an explicit `setRuleSet` on mount."

**Pattern:** For Web Worker communication, always think in terms of serializable state. Pass an identifier, resolve to behavior inside the worker. The constraint forces a cleaner separation than function callbacks would allow.

### 3 — `RULE_SETS` array as single source of truth

Amelia (Developer): "I could have hardcoded `conwayRules` and `highLifeRules` in two places: the dropdown JSX and `handleStepClick`. Instead, `RULE_SETS = [conwayRules, highLifeRules]` drives both. The dropdown maps over it; `handleStepClick` finds from it."

Quinn (QA Engineer): "Which means adding a third rule set later is: add it to `RULE_SETS`. The dropdown and the step logic both pick it up automatically."

Winston (Architect): "That's the open-closed principle expressed in four lines. No switch statement, no parallel arrays to keep in sync."

**Pattern:** When two consumers need the same list of typed objects, make the list the source of truth and let the consumers derive from it. Arrays of typed values compose better than parallel constants.

### 4 — Code review caught a real spec gap in 8-1

Quinn (QA Engineer): "The initial 8-1 spec covered B3, B6, S23-2, S23-3, and the Conway divergence. What it missed: a live cell with exactly 6 neighbors dies. HighLife S23 means survival only on 2 or 3 — 6 is not in the survival set. That case was explicitly not tested."

Amelia (Developer): "It's a subtle one. HighLife births on 6, but live cells with 6 neighbors still die. Those are different cells in different states. Easy to assume 'B6 means 6 is special' without checking what 6 means for a live cell."

Bob (Scrum Master): "Code review found it before the story shipped. That's exactly the right moment."

**Pattern:** For any rule with asymmetric behavior across cell states — birth vs. survival — write explicit tests for both states at the asymmetric value. Don't assume the birth case documents the survival behavior.

### 5 — Zero CI failures across both stories

Bob (Scrum Master): "Clean runs on both 8-1 and 8-2. No typecheck surprises, no test failures, no lint issues."

Amelia (Developer): "Epic 8 had a major advantage: no new npm installs, no CI configuration changes, no Prisma. The simpler the dependency surface, the cleaner the CI story."

**Pattern:** When an epic can be delivered with zero new runtime dependencies, treat that as a gift. The complexity budget that would have gone to `onlyBuiltDependencies` and `prisma generate` went to actual feature work instead.

## 🔍 Challenges and Learnings

### 1 — `handleStepClick` synchronization with the worker required deliberate design

Amelia (Developer): "The worker runs the simulation loop asynchronously via `tick` messages. `handleStepClick` runs synchronously on the main thread when the simulation is paused. Both need to apply the same rule set."

Winston (Architect): "The worker has `activeStep`. The main thread has `ruleSetId`. They're the same conceptually but stored differently. `RULE_SETS.find(r => r.id === ruleSetId) ?? conwayRules` is the reconciliation — look up the rule by ID the same way the worker does."

Amelia (Developer): "The `?? conwayRules` fallback is important. If `ruleSetId` somehow doesn't match any entry in `RULE_SETS`, you get the safe default rather than a crash."

**Carry-forward:** Whenever state is split across the main thread and a worker, identify every execution path that touches that state and verify both sides stay in sync. The synchronization point is a contract, not an accident.

### 2 — No story-level test existed for the rule-set switching behavior in 8-2

Quinn (QA Engineer): "8-2's acceptance criteria were verified manually. There's no Jest test that posts a `setRuleSet` message to the worker and checks that `activeStep` switches. The worker test infrastructure (mocking `OffscreenCanvas`, `postMessage`) is non-trivial to set up."

Bob (Scrum Master): "True. The grid helper tests that existed from 7-3 covered the pure logic; the worker protocol is the untested layer."

Quinn (QA Engineer): "The Playwright E2E spec covers the happy path at the UI level but doesn't exercise the rule-set selector specifically. That's a coverage gap — not a blocker, but worth noting."

**Carry-forward:** Worker message-protocol behavior is hard to unit-test without significant harness work. If future stories add complexity to the worker protocol, a dedicated worker test harness is worth building. For now, the types + the UI coverage provide reasonable confidence.

### 3 — Branch discipline held in Epic 8

Bob (Scrum Master): "This is the positive version of the challenge we'd normally flag. Epic 7 retro action item #1 was 'create branch before writing any code.' In Epic 8, both 8-1 and 8-2 had their branches created before implementation began."

Amelia (Developer): "The habit is forming. The branch wasn't Task 0 in the written task list — but it happened in the right order in practice."

Bob (Scrum Master): "Close, but not perfect. The task list for 8-1 and 8-2 didn't have an explicit 'create branch' checkbox. The behavior was right; the documentation of the behavior wasn't."

**Carry-forward:** Add 'create feature branch' as the explicit first checked task in every story file. The behavior is now consistent — the written record should match it.
